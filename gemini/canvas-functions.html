Архитектурный конспект: Функции Azure (Azure Functions)

TL;DR: Функции Azure (Azure Functions) — это флагманское бессерверное (Serverless) решение класса FaaS (Function as a Service). Оно позволяет запускать изолированные фрагменты кода в ответ на облачные события (HTTP-запросы, таймеры, очереди, изменения в БД) без необходимости администрировать серверы. Вы фокусируетесь исключительно на бизнес-логике, а платформа берет на себя масштабирование, отказоустойчивость и оплату строго за фактическое время выполнения.

Аналогия из жизни (Вендинговый аппарат):

Обычный сервер (IaaS/PaaS) — это как нанять продавца в киоск и платить ему зарплату 24/7, даже если ночью нет покупателей.
Azure Functions — это вендинговый аппарат. Он потребляет ресурсы (и ваши деньги) только в тот момент, когда кто-то нажимает кнопку (Триггер), механизм выдает товар (Ваш код) и снова переходит в спящий режим. Если наплыв покупателей резко вырос — платформа мгновенно «клонирует» десятки таких аппаратов рядом.

Модуль 1. Сценарии применения и Жизненный цикл разработки

Функции Azure выступают идеальным «клеем» для событийно-ориентированных архитектур (Event-Driven Architecture). Основные промышленные сценарии:

Модуль 2. Механика Триггеров, Привязок (Bindings) и SDK-типов

Декларативная интеграция: Главная особенность Azure Functions — вы избавляетесь от шаблонного кода (boilerplate) для создания подключений, чтения строк соединения и сериализации. Платформа сама подключается к внешним сервисам и передает готовые данные прямо в аргументы вашего метода.

Пример декларативной привязки (C# Isolated Worker Model)

Функция срабатывает по HTTP-запросу и одновременно возвращает HTTP-ответ клиенту и записывает массив сообщений в очередь Azure Queue Storage через класс MultiResponse:

[Function("HttpExample")]
public MultiResponse Run(
    [HttpTrigger(AuthorizationLevel.Function, "get", "post")] HttpRequest req)
{
    return new MultiResponse
    {
        Messages = new[] { "Заказ #1042 принят в обработку" },
        HttpResponse = new OkObjectResult("Запрос успешно поставлен в очередь!")
    };
}

public class MultiResponse
{
    [QueueOutput("outqueue", Connection = "AzureWebJobsStorage")]
    public string[] Messages { get; set; }

    [HttpResult]
    public IActionResult HttpResponse { get; set; }
}

Правило именования: Имена триггеров и привязок могут содержать только буквенно-цифровые символы и знак подчеркивания _. Все расширения привязок (кроме встроенных HTTP и Timer) должны быть явно зарегистрированы в проекте (через Extension Bundles или NuGet-пакеты).

Работа с типами пакетов SDK в привязках (SDK-Type Bindings)

Вместо примитивных строк или массивов байтов многие привязки поддерживают прямую инъекцию типизированных клиентов Azure SDK (уровень GA). Это дает строгую типизацию и доступ ко всем возможностям сервиса:

  • Blob Storage (Trigger / Input): BlobClient, BlobContainerClient, BlockBlobClient, PageBlobClient, AppendBlobClient.
  • Cosmos DB (Input): CosmosClient, Database, Container.
  • Service Bus (Trigger): ServiceBusClient, ServiceBusReceiver, ServiceBusSender, ServiceBusMessage.
  • Event Grid / Event Hubs / Queues / Tables: CloudEvent, EventData, QueueClient, TableClient, TableEntity.

Три золотых правила работы с SDK-типами:

  1. Если вы используете выражения привязки (например, {name} из триггера для пути во входной привязке), вы не можете использовать SDK-тип в самом триггере.
  2. Для сложных сценариев вывода (Output) рекомендуется создавать клиент SDK напрямую через Dependency Injection, а не использовать выходную привязку.
  3. Триггер Cosmos DB не поддерживает SDK-типы, так как канал изменений (Change Feed) всегда передает сериализованный JSON.

Модуль 3. Устойчивые функции (Durable Functions)

TL;DR: Обычные функции Azure не хранят состояние (stateless) и имеют ограничения по времени выполнения. Durable Functions — это расширение, позволяющее писать функции-оркестраторы с сохранением состояния (stateful) прямо в коде. Платформа сама сохраняет контрольные точки (checkpoints) в хранилище, «усыпляет» оркестратор во время ожидания и пробуждает его при получении результата — вы не платите за время простоя!

Модуль 4. Варианты хостинга (Hosting Plans)

Выбор плана хостинга определяет модель биллинга, наличие проблемы «холодного старта» (Cold Start), сетевую изоляцию (VNet) и максимальное время выполнения функции.

План хостинга Масштабирование и Оплата Ключевые особенности и Сценарии (Use Case)
Flex Consumption
(Рекомендуемый стандарт)		 Сверхбыстрое событийное масштабирование (до 0). Оплата строго по мере использования (Pay-as-you-go). Поддержка интеграции с VNet, выбор размера памяти экземпляра, опциональные «всегда готовые» экземпляры для устранения холодного старта. Примечание: редактирование кода на портале Azure не поддерживается (только локальная разработка/CI-CD).
План «Премиум» (Elastic Premium) Событийное масштабирование с предварительно прогретыми экземплярами. Оплата за выделенные ядра/RAM. Нулевой холодный старт, неограниченная длительность выполнения (по умолчанию 30 мин, настраивается), полная поддержка VNet и пользовательских образов Linux. Идеально для критичных к задержкам API.
Выделенный план (Dedicated / App Service Plan) Ручное или авто-масштабирование по метрикам (CPU/RAM). Фиксированная ежемесячная стоимость. Запуск функций на уже оплаченных серверах вместе с веб-сайтами. Прогнозируемый бюджет. Обязательно включите опцию Always On.
Azure Container Apps (ACA) Событийное масштабирование на базе Kubernetes (KEDA), включая масштаб до 0. Развертывание контейнеризированных функций бок о бок с другими микросервисами, Dapr и пользовательскими библиотеками в единой среде.
План потребления (Classic Consumption) Устаревающий бессерверный план. Внимание: Поддержка Linux Consumption прекращается 30 сентября 2028 г. (новые версии .NET выше .NET 9 туда не добавляются). Windows-версия пока активна, но для всех новых проектов используйте Flex Consumption.

Модуль 5. Языки программирования, ОС и Модели процессов

Критическая дорожная карта поддержки (Lifecycle & Deprecation)

  • C# In-Process Model (Модель в процессе): Поддержка завершилась 10 ноября 2026 года (поддерживала максимум .NET 8 LTS). Все корпоративные приложения должны работать на Изолированной рабочей модели (Isolated Worker Model), которая поддерживает .NET 8, .NET 9 и актуальный .NET 10 (GA до 14 ноября 2028 г.).
  • Среда выполнения v3 на Linux Consumption: Перестала функционировать после 30 сентября 2026 г. Необходима миграция на runtime v4.x.
  • Linux Classic Consumption: Полный вывод из эксплуатации запланирован на 30 сентября 2028 г. (целевой план миграции — Flex Consumption).
  • Обновление управляемых образов Linux: Для существующих приложений Python 3.11 и Java 8/11/17 на планах Elastic Premium / Dedicated рекомендуется переходить с устаревающего образа Debian Bullseye (|2.0) на Debian Bookworm (Python|3.11|3.0) и Ubuntu Noble (Java|17|4.0).

Isolated Worker Model (C#)

Ваше приложение-функция запускается как самостоятельный процесс .NET и общается с хостом Azure Functions по высокоскоростному каналу gRPC. Это полностью устраняет конфликты версий NuGet-пакетов с хостом, дает полноценный Program.cs, стандартное внедрение зависимостей (DI) и конвейер Middleware.

Пользовательские обработчики (Custom Handlers)

Если ваш язык официально не поддерживается (например, Rust или специфическая версия Go), вы пишете легковесный HTTP-сервер. Хост Azure Functions принимает все облачные триггеры (Queue, Blob, Timer), пересылает их вашему локальному HTTP-серверу, а ответ преобразует в выходные привязки.

Модуль 6. Архитектурные Best Practices и Anti-patterns

✔ Правильно (Best Practices):
  • Пишите идемпотентные функции: В распределенных системах сообщения из очередей могут доставляться повторно (At-least-once). Повторный запуск функции с тем же ID заказа не должен приводить к двойному списанию денег.
  • Переиспользуйте клиенты подключений (Static / Singleton): Регистрируйте HttpClient, CosmosClient и ServiceBusClient как Singleton через DI. Создание нового клиента на каждый вызов функции быстро исчерпает лимит исходящих TCP-сокетов (SNAT Port Exhaustion).
  • Не закрепляйте минорные версии языков: Azure автоматически обновляет патчи безопасности (например, Python 3.11.x) и удаляет устаревшие минорные сборки. Ориентируйтесь только на мажорную версию.
  • Используйте Managed Identity вместо строк подключения: Подключайтесь к Blob Storage, Key Vault и Service Bus через управляемое удостоверение Entra ID, чтобы не хранить секреты в настройках приложения.
✖ Неправильно (Anti-patterns):
  • Длительные синхронные задачи в HTTP-функциях: Не заставляйте HTTP-запрос ждать 5 минут. Вместо этого быстро примите запрос, положите задачу в очередь (или запустите Durable Function) и верните статус 202 Accepted.
  • Межфункциональные вызовы по HTTP: Избегайте прямого вызова одной функции из другой по HTTP — это создает жесткую связанность и двойную оплату за время ожидания. Используйте очереди (Service Bus / Storage Queues) или оркестратор Durable Functions.
  • Хранение состояния в локальной памяти: Экземпляр функции может быть уничтожен платформой в любую секунду после завершения работы. Всегда сохраняйте состояние во внешнем хранилище.

Сводка и Итоги

Завершено | Получено XP: 350

Azure Functions — это универсальный строительный блок современных облачных и ИИ-решений, позволяющий платить только за реальную бизнес-логику.

  • События и Привязки: Один триггер запускает код, а декларативные входные/выходные привязки (включая SDK-типы, Managed Connectors и MCP для ИИ) избавляют от рутинной интеграции.
  • Оркестрация (Durable Functions): Позволяет строить надежные цепочки и параллельные вычисления (Fan-out/Fan-in) без оплаты времени простоя.
  • Современный хостинг: Flex Consumption — целевой стандарт для новых бессерверных систем (быстрое масштабирование + VNet).
  • Архитектура процессов: Используйте Isolated Worker Model для C# (.NET 8–10) и Custom Handlers для нестандартных языков вроде Rust.
