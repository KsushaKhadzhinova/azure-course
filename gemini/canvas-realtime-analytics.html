Архитектурный конспект: Основы аналитики в реальном времени

TL;DR: Не все данные могут ждать ночной загрузки. Аналитика в реальном времени (Streaming) позволяет мгновенно реагировать на события (транзакции, датчики IoT). Современная архитектура объединяет надежность пакетной обработки исторических данных со скоростью потоковой передачи для оперативных решений.

Модуль 1. Пакетная (Batch) против Потоковой (Stream) обработки

Аналогия из жизни (Подсчет автомобилей):
  • Пакетная обработка (Batch): Вы собираете все проезжающие автомобили на огромной парковке. В конце дня вы закрываете парковку и считаете все машины разом. Плюс: Можно точно пересчитать огромные объемы. Минус: Вы узнаете результат только завтра.
  • Потоковая обработка (Stream): Вы ставите лазерный датчик над дорогой. Он считает каждую машину в ту же миллисекунду, как она проехала, и рисует график за последние 60 секунд. Вы не ждете, вы видите тренд прямо сейчас!
Рис 1. Пакетная обработка: Сбор данных -> Хранение (Ожидание) -> Обработка всего пула.
Рис 2. Потоковая обработка: Данные обрабатываются мгновенно, группируясь по временным окнам (Time Windows).

Модуль 2. Архитектура Lambda (Объединение двух миров)

Под капотом (Deep Dive): Лямбда-архитектура

Крупным корпорациям нужны как точные исторические отчеты, так и оперативные метрики. Лямбда-архитектура решает это, разветвляя входящий поток данных на два пути:

  1. Холодный путь (Batch Layer): Данные сбрасываются в Data Lake и обрабатываются раз в сутки.
  2. Горячий путь (Speed Layer): Данные летят в потоковый процессор для мгновенного отображения.
  3. Уровень обслуживания (Serving Layer): Объединяет результаты обоих путей для конечного пользователя.
Рис 3. Шаблон Лямбда-архитектуры. Данные (1) разветвляются на пакетное хранилище (2,3,5) и на потоковую обработку в реальном времени (4,6) для визуализации (7).

Модуль 3. Элементы потоковой архитектуры (Sources & Sinks)

Рис 4. Конвейер потока: Источник (События) -> Очередь (Queue) -> Непрерывный запрос (Perpetual Query) -> Приемник (Sink).

Любой потоковый конвейер состоит из трех фундаментальных слоев:

Слой Роль Службы Azure
1. Источник (Source/Queue) Буферизирует миллионы событий в секунду и гарантирует доставку.
Лимиты Event Hubs: Размер сообщения до 1 МБ (Standard) или до 20 МБ (Dedicated), до 32 разделов (в базовых уровнях), срок хранения данных — до 90 дней (в Premium).		 Azure Event Hubs, Azure IoT Hub, Apache Kafka.
2. Потоковый процессор Агрегирует данные по времени и фильтрует события "на лету".
Лимиты Stream Analytics: Жесткое ограничение в 60 входов, 60 выходов и 60 функций на 1 задание (Job). Максимум 66 потоковых единиц (SU) на задание.		 Azure Stream Analytics, Spark Structured Streaming, Fabric Eventstream.
3. Приемник (Sink) Куда сбрасывается результат обработки. Power BI, Data Lake, Cosmos DB, Eventhouse (KQL).

Модуль 4. Продвинутая архитектура: Fabric Real-Time Intelligence

Microsoft Fabric Real-Time Intelligence — это SaaS-подсистема для работы с телеметрией "под ключ". Она включает маршрутизацию, СУБД для временных рядов (Eventhouse) и автоматизированные реакции (Активатор).

Рис 5. Экосистема Real-Time Intelligence в Fabric. Включает Eventstream (Прием), Eventhouse (Хранение), Reflex (Триггеры) и Real-Time Hub.

Инновационные возможности (Deep Dive)

  • Eventhouse и KQL: Специализированная колоночная база данных для временных рядов. Kusto Query Language (KQL) оптимизирован для полнотекстового поиска и агрегаций миллиардов строк телеметрии за миллисекунды.
  • Data Activator (Reflex): Система автоматического реагирования без кода. Позволяет настраивать триггеры на потоки или визуализации Power BI.
  • AI Copilot и MCP Агенты (Preview): Интеграция Copilot позволяет писать KQL-запросы на естественном языке ("Покажи среднюю температуру датчика X за 5 минут"). Более того, внедрена поддержка серверов Model Context Protocol (MCP), что позволяет внешним ИИ-агентам безопасно взаимодействовать с Eventhouse и Активатором.
  • Цифровые двойники (Digital Twins - Preview): Позволяет создавать виртуальные копии физических объектов (например, завода) и привязывать к ним живые потоки данных телеметрии для мониторинга в реальном времени.

Модуль 5. Apache Spark Structured Streaming (Под капотом)

Принцип бесконечной таблицы

Для хардкорной инженерии в Azure Databricks и Fabric Spark используется Spark Structured Streaming. Его фундаментальная идея: вы работаете с потоком так, будто это обычная статичная таблица (DataFrame), к которой снизу постоянно приписываются новые строки.

Рис 6. Spark Structured Streaming. Поток превращается в бесконечно растущий Dataframe. Запрос применяется инкрементально.

Архитектурные компромиссы обработки (Modes)

Под капотом Spark позволяет выбрать один из двух режимов работы движка в зависимости от жесткости ваших SLA:

Режим (Processing Mode) Механика работы Задержка (Latency) Отказоустойчивость
Micro-batch (По умолчанию) Движок накапливает данные за долю секунды и запускает мини-пакетную задачу. ~ 100 миллисекунд Exactly-once (Строго один раз). Достигается за счет механизмов Checkpointing и Write-Ahead Logs (WAL).
Continuous Processing (С версии Spark 2.3) Непрерывная конвейерная обработка каждого события (как в Apache Flink). ~ 1 миллисекунда At-least-once (Хотя бы один раз). Подходит для сценариев, где микросекунды критичнее случайного дубля данных.

Модуль 7. Глубокое погружение: Lakehouse и Delta Tables в Fabric

TL;DR: Delta Lake — это открытый формат хранения по умолчанию для всех таблиц Lakehouse в Fabric. Он объединяет скорость аналитики Parquet-файлов с транзакционной надежностью базы данных (ACID). Fabric обрабатывает дельта-форматирование и автоматическую оптимизацию (V-Order) в фоновом режиме.

Под капотом: Настройки Spark (Fabric vs Synapse)

Fabric использует среду выполнения Apache Spark, но с агрессивными оптимизациями "из коробки", которые отличают её от классического Azure Synapse Analytics.

Конфигурация Spark Fabric (по умолчанию) Synapse Analytics Бизнес-значение
spark.sql.sources.default delta parquet Любой сохраненный DataFrame автоматически становится транзакционной Delta-таблицей, без ручного указания формата.
spark.sql.parquet.vorder.default true (в средах до 1.3) N/A Проприетарная сортировка данных Microsoft (V-Order), которая кардинально ускоряет чтение файлов Parquet движком Power BI (Direct Lake).
Автоматическое обнаружение и Ярлыки (Shortcuts):

Fabric Lakehouse автоматически сканирует OneLake и отображает найденные таблицы в разделе Tables. Но что если данные лежат во внешней системе?

  • Внешняя Delta-таблица (ADLS/S3): Создавайте ярлык в раздел Tables. Fabric сразу распознает её как готовую SQL-таблицу.
  • Сырые CSV/JSON файлы или папки: Создавайте ярлык строго в раздел Files. Затем используйте Spark для чтения этих файлов (схема при чтении) и трансформации их в Delta-таблицу внутри Lakehouse.
  • Устаревшие таблицы Apache Hive: Создавайте ярлык в Files и используйте CREATE EXTERNAL TABLE в Spark.
