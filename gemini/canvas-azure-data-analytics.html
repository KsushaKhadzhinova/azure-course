Архитектурный конспект: Аналитика больших данных в Azure

TL;DR: Крупномасштабная аналитика объединяет традиционные хранилища (Data Warehouse) с большими озерами данных (Data Lake), порождая архитектуру Lakehouse. В Azure двумя столпами современной аналитики являются Microsoft Fabric (SaaS "всё включено") и Azure Databricks (PaaS на базе Apache Spark).

Аналогия из жизни (Водопровод и Завод по розливу воды):

Сбор данных похож на добычу воды из разных источников (дождь, реки, скважины).

  • Data Lake (Озеро): Огромный природный резервуар. Сюда стекает вода (данные) в любом виде. Хранить дешево, но пить (анализировать) напрямую сложно.
  • Data Warehouse (Склад): Завод, где воду очистили и разлили по строгим 5-литровым бутылкам (реляционные таблицы). Идеально для продажи, но дорого и долго.
  • Lakehouse: Вы ставите фильтры и краны прямо на озере. Вы получаете и низкую цену хранения озера, и чистоту/структуру завода.

Модуль 1. Архитектура крупномасштабной аналитики

Рис 1. Классическая архитектура: Системы-источники -> Уровень хранения (Хранилище/Озеро/Lakehouse) -> Аналитика и Визуализация.

Любое аналитическое решение строится на 5 обязательных этапах:

Рис 2. Конвейер: 1) Прием (Ingest), 2) Хранение, 3) Семантическая модель, 4) Визуализация, 5) ИИ-ассистенты (Copilot).
  1. Прием и обработка (ETL / ELT): Извлечение из OLTP-баз, очистка и загрузка. При пакетной обработке данные переносятся по расписанию. При потоковой — в реальном времени.
  2. Аналитическое хранилище: Место, где данные лежат физически (Warehouse, Lake, Lakehouse).
  3. Семантическая модель: Прослойка бизнес-логики. Вместо старых "OLAP-кубов", сейчас строятся табличные модели (с использованием языка DAX), где меры вычисляются на лету. В Fabric режим Direct Lake позволяет читать данные прямо из OneLake без копирования!
  4. Визуализация: Дашборды в Power BI для принятия управленческих решений.
  5. ИИ-Аналитика: Copilot в Fabric и Genie в Databricks позволяют задавать вопросы к данным на естественном языке, генерируя SQL или DAX "под капотом".

Модуль 2. Эволюция хранилищ: Warehouse vs Lake vs Lakehouse

1. Data Warehouse (Хранилище данных)

Реляционная база данных, оптимизированная не для записи транзакций, а для чтения гигантских агрегаций. Данные организуются в схему «Звезда» (Star Schema) или «Снежинка» (Snowflake Schema), состоящую из таблиц Фактов (цифры, продажи) и таблиц Измерений (категории, даты, клиенты).

Рис 3. Слева: Схема Звезда (денормализованные измерения). Справа: Снежинка (измерения нормализованы). Звезда работает быстрее для аналитики.

2. Data Lake (Озеро данных)

Распределенная файловая система. Использует подход «Схема при чтении» (Schema-on-read). Вы просто сваливаете сырые JSON, CSV и Parquet в озеро. А когда Apache Spark читает их, он "натягивает" на них табличную структуру в оперативной памяти.

Рис 4. Принцип работы озера: храним любые форматы (Schema-on-write), а структуру задаем только в момент запроса (Schema-on-read).

3. Data Lakehouse (Гибрид)

Необработанные данные лежат в Озере (дешево), но поверх них добавляется транзакционный слой (Delta Lake). Это позволяет использовать SQL-запросы (как в Warehouse), обеспечивая ACID-транзакции прямо поверх файлов Parquet.

Рис 5. Lakehouse объединяет лучшие черты складов и озер. Стандарт индустрии — формат Delta Lake.

Модуль 3. Инструменты приема данных (Data Ingestion)

Рис 6. Конвейеры Ingestion: Источники -> Фабрики данных / Shortcuts / Databricks -> Lakehouse.

Как данные попадают в хранилище? Платформы предлагают разные инструменты:

Механизм Платформа Как это работает
Data Factory (Pipelines / Dataflows Gen2) Fabric & Azure Low-code интерфейс. Pipelines оркестрируют шаги, Dataflows трансформируют данные визуально.
Лимиты: До 5 000 сущностей на фабрику, 10 000 одновременных запусков конвейеров, максимум 120 активностей в одном конвейере.
Shortcuts (Ярлыки) Fabric (OneLake) Zero Copy! Виртуальная ссылка на Amazon S3 или ADLS. Данные не копируются, но доступны для SQL.
Mirroring (Зеркалирование) Fabric Автоматическая непрерывная репликация из Cosmos DB или Snowflake в OneLake в реальном времени. Без создания пайплайнов!
Eventstream Fabric Перехват потоковых данных (Kafka, IoT) и маршрутизация их в KQL базы данных (Eventhouse).
Lakeflow Pipelines / Auto Loader Databricks Декларативные пайплайны на базе Spark, которые автоматически обрабатывают новые файлы (инкрементально) по мере их появления.

Архитектурные ограничения рабочих областей (Synapse & ADF Limits)

Для предотвращения влияния рабочих нагрузок одних клиентов на других ("шумные соседи"), в Azure применяются следующие квоты:

  • Azure Synapse Analytics: Допускается создание до 20 рабочих областей на регион (увеличивается до 100 через техподдержку). Внутри одной рабочей области можно создать максимум 800 конвейеров (pipelines).
  • Среды Integration Runtime (IR): Количество связанных узлов Self-Hosted IR ограничено 100 на фабрику данных. Лимит вычислительных единиц (DIU) для копирования в Azure IR может достигать 6000 DIU для основных регионов.
  • Полезная нагрузка активностей: Максимальный размер полезной нагрузки (payload) для каждого запуска активности строго ограничен 896 КБ. Это необходимо учитывать при передаче больших массивов параметров между шагами.

Модуль 4. Современный стек: Microsoft Fabric vs Azure Databricks

Архитектурный выбор платформы:
  • Microsoft Fabric (SaaS): Выбирайте, если нужна платформа "всё включено" для всей компании. Не нужно управлять серверами. Единый OneLake. Интеграция Lakehouse, Warehouse и Power BI "из коробки". Фокус на простоте и Low-Code.
  • Azure Databricks (PaaS): Выбирайте, если у вас мощная команда Data-инженеров, пишущая сложный код на Python/Scala. Высшая производительность Spark, гибкий контроль над кластерами, межоблачная переносимость (работает в AWS/GCP). Единый слой управления Unity Catalog.

Модуль 5. Практическая лаборатория (Fabric Lakehouse & SQL Endpoint)

TL;DR: В Microsoft Fabric аналитика начинается с создания Рабочей области (Workspace) с включенной емкостью (Capacity). Внутри нее мы создаем Lakehouse, импортируем сырые данные через Copy Job (без кода) и мгновенно анализируем их через SQL.

Шаг 1. Создание рабочей области (Workspace)

Рабочая область — это папка проекта. Включение лицензии "Fabric / Trial" дает ей вычислительные мощности.

1. Переключение на Data Engineering Experience в меню Fabric.
2. Нажатие + New workspace в боковом меню.
3. Указание имени и выбор лицензии Capacity (Premium/Trial).
4. Пустая рабочая область готова к созданию Lakehouse.

Шаг 2. Создание Lakehouse

Lakehouse объединяет гибкость файлового хранилища с транзакционностью баз данных. Создадим его в нашей новой рабочей области.

1. Выбор элемента Lakehouse в меню New item.
2. Присвоение имени (например, taxi_lakehouse) и создание.

Шаг 3. Загрузка данных (Data Ingestion) через Copy Job

Чтобы не писать код на Python/Spark для загрузки сырых файлов, мы используем мастер Copy Job. Он позволит импортировать открытый набор данных (NYC Taxi) и сохранить его напрямую в виде управляемой таблицы (Tables) в формате Delta.

1. Запуск мастера копирования (Get data -> New copy job).
2. Создание задачи Ingest Data.
3. Выбор открытого датасета (NYC Taxi - Green) из вкладки Sample data.
4. Настройка: Full copy (Полная копия) с записью в папку Tables (создание Delta-таблицы).
5. Маппинг: Назначение схемы dbo и имени таблицы (taxi_rides).
6. Проверка настроек (Review + save) и немедленный запуск (Save + Run).
7. Успешное выполнение конвейера (Status: Succeeded).
8. Появление готовой таблицы taxi_rides в интерфейсе Lakehouse Explorer.

Шаг 4. SQL-Аналитика

Как только Copy Job завершается, Fabric автоматически генерирует SQL Analytics Endpoint (Конечную точку аналитики SQL). Переключившись на нее, можно писать стандартные SQL-запросы прямо в браузере, например:

1. Переключение контекста Lakehouse на SQL analytics endpoint.
2. Написание и запуск (Run) агрегирующего T-SQL запроса.
SELECT DATENAME(dw, lpepPickupDatetime) AS Day,
       AVG(tripDistance) As AvgDistance
FROM taxi_rides 
GROUP BY DATENAME(dw, lpepPickupDatetime)

Результат: Система группирует поездки по дням недели и вычисляет среднюю дистанцию, сканируя Parquet-файлы "под капотом" с помощью T-SQL движка.
