Архитектурный конспект: Нереляционные хранилища Azure (Blob Storage)

TL;DR: Не всем данным нужна жесткая реляционная схема SQL. Azure Blob Storage — это фундаментальная служба для хранения петабайтов неструктурированных файлов (изображений, логов, бэкапов). Она обеспечивает масштабируемость, гранулярный контроль доступа (RBAC), управление жизненным циклом и аппаратную отказоустойчивость.

Служба хранилища Azure аппаратно оптимизирует запись и чтение в зависимости от того, как ваше приложение работает с файлом. При проектировании Enterprise-систем критически важно знать системные ограничения (Limits).

Блочные (Block Blobs) Файл делится на независимые блоки (до 4000 МиБ в новых версиях API).
Максимальное количество блоков: 50 000.
Макс. размер файла: ~190,7 ТиБ.
Целевая пропускная способность: до 3000 запросов в секунду.		 Хранение картинок, видео, документов, статических веб-сайтов. (Обычные файлы).
Страничные (Page Blobs) Массив страниц по 512 байт. Можно читать и писать данные в случайную позицию мгновенно.
Макс. размер файла: 8 ТиБ.
Целевая пропускная способность: до 500 запросов в секунду.		 Фундамент для дисков Виртуальных машин Azure (VHD). Базы данных.

Макс. размер файла: ~195 ГиБ.		 Идеально для потоковой записи системных журналов (логов), метрик телеметрии IoT.

Масштабируемость аккаунта Storage (GPv2)

Для стандартной учетной записи хранения (General Purpose v2) Azure применяет следующие жесткие квоты (лимиты), которые можно повысить только через запрос в техподдержку:

  • Емкость аккаунта (Capacity): 5 PiB (Пебибайт).
  • Транзакции управления (Control Plane): Операции чтения (например, список аккаунтов) ограничены 800 запросов за 5 минут. Операции записи — 10 в секунду.
  • Входящий трафик (Ingress): От 25 до 60 Гбит/с в зависимости от региона.
  • Исходящий трафик (Egress): От 50 до 200 Гбит/с в зависимости от региона.
  • Лимит запросов (Data Plane): 20 000 – 40 000 запросов в секунду.

Trade-offs (Компромиссы уровней доступа)

Архитектура хранения всегда балансирует между стоимостью хранения 1 ГБ и стоимостью/задержкой чтения.

Уровень Стоимость хранения Штраф за раннее удаление Бизнес-контекст
Горячий (Hot) Самая высокая Нет Активные данные приложения. Чтение/запись происходят прямо сейчас (например, аватарки активных юзеров).
Холодный (Cool) Ниже Минимум 30 дней Данные, к которым обращаются 1-2 раза в месяц. (Отчеты за прошлый месяц).
Архив (Archive) Копейки (Lowest) Минимум 180 дней Законодательные архивы, логи за 5 лет. Важно: Блоб в оффлайне. Для чтения требуется процесс восстановления (rehydration), занимающий до 15 часов.

Модуль 3. Стратегии избыточности (Redundancy)

Под капотом (Deep Dive): Репликация данных

Azure никогда не хранит файл в одном экземпляре. По умолчанию всегда создается минимум 3 копии.

  • LRS (Locally Redundant): 3 копии в одной стойке/серверной. Если сгорит ЦОД — данные потеряны.
  • ZRS (Zone-Redundant): Копии распределены по 3 разным зданиям (зонам доступности) внутри одного региона.
  • GRS (Geo-Redundant): LRS в основном регионе + асинхронная репликация LRS в резервный регион (за сотни километров).
  • GZRS (Geo-Zone-Redundant): Максимальная защита. ZRS в основном регионе + репликация LRS в резервный регион.

Бизнес-контекст: Добавление префикса RA- (Read-Access) к гео-опциям позволяет приложению переключиться на чтение из резервного региона при сбое.

Модуль 4. ADLS Gen2, Azure Files, Tables и Queues

Azure Data Lake Storage Gen2 (ADLS) добавляет к Blob-хранилищу иерархическое пространство имен (HNS). Папки становятся реальными объектами, что позволяет назначать POSIX-права и мгновенно переименовывать гигантские каталоги (Оптимизация для Big Data / Apache Spark).

Лимиты других служб Azure Storage

Для полноты картины инфраструктуры, рассмотрим аппаратные ограничения смежных служб хранения:

Служба Назначение Жесткие лимиты (Limits & Quotas)
Azure Table Storage Быстрая NoSQL БД (Ключ-Значение) Макс. размер одной таблицы: 500 ТиБ.
Макс. размер сущности (строки): 1 МиБ (до 255 свойств).
Пропускная способность: до 20 000 транзакций в секунду на аккаунт.
Azure Queue Storage Обмен сообщениями между микросервисами Макс. размер одной очереди: 500 ТиБ.
Макс. размер сообщения: 64 КиБ.
Пропускная способность: до 2000 сообщений в сек. для одной очереди.
Azure Files Сетевые диски (SMB / NFS) Premium-уровень (SSD) поддерживает емкость до 256 ТиБ. Макс. размер одного файла: 4 ТиБ.
Best Practices vs. Anti-patterns:
✔ Правильно (Best Practice): Включать иерархическое пространство имен (HNS) при создании учетной записи хранения, если вы планируете использовать её как Data Lake.
✖ Неправильно (Anti-pattern): Размещать реляционные данные с жесткими связями в Azure Table Storage. Azure Table не поддерживает JOIN, а для высокой производительности требует обязательного указания PartitionKey в фильтре запроса.
