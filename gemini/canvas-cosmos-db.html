Архитектурный конспект: Azure Cosmos DB и Экосистема NoSQL

TL;DR: Реляционные базы данных (SQL) идеальны для строгих схем, но их сложно глобально масштабировать. Azure Cosmos DB — это полностью управляемая PaaS-служба NoSQL баз данных. Она не зависит от схемы (schema-agnostic), гарантирует задержку <10 миллисекунд по всему миру, обладает SLA 99,999% и поддерживает 5 различных API (NoSQL, MongoDB, Cassandra, Gremlin, Table) под капотом одного движка.

Аналогия из жизни (Библиотека vs Интернет-поиск):

Реляционная БД — это классическая библиотека. Каждая книга (строка) должна иметь строгую карточку: Автор, Год, Жанр (колонки). Если вы принесете аудиокассету, библиотекарь откажется её принять, так как для неё нет колонок в картотеке. Чтобы изменить картотеку, нужно закрыть библиотеку на ремонт (миграция схемы).

Cosmos DB (NoSQL) — это поисковая система в интернете. Вы можете «закинуть» туда текстовую статью, видео или товар с 50 уникальными характеристиками. Система автоматически проиндексирует каждое слово (Automatic Indexing) и мгновенно найдет нужный документ, независимо от его структуры.

Под капотом (Deep Dive): Физическое секционирование

Cosmos DB обеспечивает бесконечное горизонтальное масштабирование благодаря механизму секционирования. Контейнер — это логическая единица, но под капотом данные разбиваются на физические серверы на основе Ключа секции (Partition Key).

Ограничение: Одна логическая секция (все документы с абсолютно одинаковым значением Partition Key) не может превышать размер в 20 ГБ.

Best Practices vs. Anti-patterns (Выбор ключа партиционирования):
✔ Правильно (Best Practice): Выбирать ключ с высокой кардинальностью (множеством уникальных значений), например /DeviceId для IoT или /UserId для профилей. Это равномерно распределит нагрузку (хранение и запросы) по всем серверам кластера.
✖ Неправильно (Anti-pattern): Выбрать ключ /City, если 90% ваших пользователей живут в одном городе. Один физический сервер возьмет на себя 90% нагрузки и станет "горячей точкой" (Hot Partition), быстро упрется в лимит 20 ГБ, а остальные серверы будут простаивать.

Модуль 2. Экономика производительности (Единицы Запроса - RU/s)

В Cosmos DB вы не арендуете процессоры или гигабайты оперативной памяти. Валютой производительности является Единица запроса (Request Unit - RU/s). Это синтетическая метрика, объединяющая CPU, IOPS и RAM. 1 RU = стоимость чтения 1 документа размером 1 КБ по его ID и ключу секции.

Компромиссы: Модели пропускной способности

Режим Как это работает Бизнес-сценарий
Выделенная (Dedicated) Резервирование RU/s для конкретного контейнера. Микросервис с предсказуемо высокой нагрузкой. Гарантия того, что "соседние" контейнеры не отберут ресурсы.
Совместная (Shared) Бюджет RU/s выделяется на уровне Базы данных и делится между 25 контейнерами. Множество мелких таблиц, которые редко нагружаются одновременно. Экономия средств.
Бессерверная (Serverless) Отсутствие резервирования. Оплата строго за потребленные RU за каждый запрос. Pet-проекты, тестирование, приложения с непредсказуемым редким трафиком (Spiky workloads). Ограничено 1 регионом!
Автомасштабирование Cosmos DB автоматически меняет RU/s в заданном диапазоне (например, от 400 до 4000). Крупный E-commerce, где нагрузка зависит от времени суток (распродажи).

Модуль 3. Глобальное распределение и уровни согласованности (CAP-теорема)

Рис 2. Компромисс между задержкой (доступностью) и строгой консистентностью. Session — выбор по умолчанию.

Под капотом (Deep Dive): Компромиссы согласованности (Trade-offs)

Согласно CAP-теореме, распределенная база не может одновременно обеспечить идеальную Согласованность (Consistency) и Доступность (Availability) при разделении сети. Cosmos DB дает разработчику 5 "ручек" для тюнинга этого компромисса:

Уровень Суть Цена (Trade-off)
Сильная (Strong) Вы всегда читаете последнюю записанную версию. Как в реляционной БД на одном сервере. Самая высокая задержка записи. Запись должна быть подтверждена всеми репликами на планете.
Session (Сеанс) [Рекомендуемый] Вы гарантированно видите собственные записи внутри одной сессии (приложения). Пользователь на другом континенте может увидеть ваш комментарий с задержкой в пару миллисекунд.
В конечном счете (Eventual) Данные когда-нибудь синхронизируются. Самая высокая доступность и минимальная задержка, но данные могут читаться в случайном порядке.

Рис 3. Cosmos DB выступает единым универсальным движком для разных языков запросов и моделей данных.

Базовый формат хранения в Cosmos DB — ARS (Atom-Record-Sequence). Поверх этого слоя работают API-трансляторы, позволяющие мигрировать приложения без переписывания драйверов БД.

API Формат / Язык Лучший сценарий (Use Case)

MongoDB BSON / MQL Миграция существующих приложений (MEAN/MERN стек) на базе MongoDB.

Модуль 5. Практическая лаборатория (Provisioning & Data Explorer)

TL;DR: Cosmos DB содержит встроенный инструмент Data Explorer прямо в Azure Portal. Он позволяет управлять контейнерами, создавать документы JSON вручную и писать SQL-запросы без установки дополнительных IDE.

Шаг 1. Развертывание (Provisioning) Azure Cosmos DB

Процесс создания начинается в Azure Marketplace. Важно правильно выбрать API, так как его нельзя изменить после создания аккаунта.

1. Поиск Azure Cosmos DB в Marketplace.
2. Выбор NoSQL API для нативной работы с JSON.
3. Выбор типа рабочей нагрузки (Learning) для минимизации затрат.
4. Валидация настроек (Review + create) и оценка времени.
5. Панель Overview готового ресурса Cosmos DB (статус Online, режим Capacity и локации).

Шаг 2. Работа с данными (Data Explorer)

Создание нового JSON Item. Обратите внимание на автосгенерированные системные поля (начинаются с _, например _ts - timestamp).
Выполнение SQL-запроса SELECT * FROM c WHERE CONTAINS(c.name, "Helmet") к JSON-документам.

Под капотом (Deep Dive): Системные свойства JSON

При сохранении документа Cosmos DB автоматически добавляет метаданные для маршрутизации и оптимистичной блокировки (Optimistic Concurrency Control):

  • id — Уникальный идентификатор (обязателен).
  • _rid — Внутренний идентификатор маршрутизации Cosmos DB.
  • _etag — Тег сущности. Важнейшее поле для транзакций! Если два пользователя одновременно редактируют документ, база проверит _etag и отклонит вторую запись, защитив данные от перезаписи.

В реальных приложениях разработчики не используют Data Explorer, а подключаются через SDK (C#, Python, Node.js), маршрутизируя запросы к NoSQL API.
