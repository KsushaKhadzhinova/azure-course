Архитектурный конспект: Службы баз данных в Azure

Модуль 1. Семейство служб Azure SQL (Microsoft SQL Server)

TL;DR: Azure предлагает 4 варианта развертывания SQL Server. Ваш выбор зависит от одной вещи: вы мигрируете старое приложение или создаете новое? Чем больше аспектов инфраструктуры Azure берет на себя (PaaS), тем меньше ваших затрат на администрирование.

Аналогия из жизни (Жилищный вопрос):
  • SQL Server на Виртуальной машине (IaaS): Аренда пустого дома. У вас есть доступ к операционной системе (ОС Windows/Linux). Вы сами ставите антивирусы, обновляете ОС и делаете бэкапы. Максимум контроля, но и максимум головной боли.
  • Управляемый экземпляр (Managed Instance - PaaS): Апартаменты с обслуживанием. Вы не имеете доступа к ОС, но база выглядит на 100% как ваш старый локальный сервер. Работают старые функции (Linked Servers, SQL Agent). Идеально для "бесшовного" переезда в облако без переписывания кода (Lift-and-Shift).
  • База данных SQL Azure (Single Database - PaaS): Номер в смарт-отеле. Вы получаете только саму базу. Все ресурсы изолированы, масштабирование происходит в 1 клик. Идеально для современных микросервисов (Cloud-Native).
  • Эластичный пул (Elastic Pool): Корпоративный тариф. У вас 100 баз данных (например, SaaS-продукт для разных клиентов). Они не активны одновременно. Вы покупаете общий "пул ресурсов" (CPU/RAM), и базы делят его между собой. Колоссальная экономия!

Под капотом (Deep Dive): Вычислительные уровни (DTU vs vCore)

При создании базы в Azure вам предложат выбрать модель оплаты и производительности:

  • Модель DTU (Database Transaction Unit): "Комплексный обед". Процессор, память и скорость диска связаны в одну метрику (DTU). Дешево, просто, идеально для старта.
  • Модель vCore (Виртуальные ядра): "Шведский стол". Вы отдельно выбираете количество ядер CPU и отдельно размер/скорость диска. Нужна для тяжелых корпоративных нагрузок и прозрачного планирования бюджета.
  • Serverless (Бессерверная конфигурация): Уникальная фича Azure SQL Database. База тарифицируется посекундно. Если ночью к ней нет обращений — она засыпает (ставится на автопаузу), и вы платите только за хранение гигабайтов на диске!

Trade-offs (MySQL vs PostgreSQL)

Характеристика Azure Database for MySQL Azure Database for PostgreSQL
Парадигма Чисто реляционная СУБД. Объектно-реляционная СУБД (поддерживает массивы, JSONB, наследование).
Расширяемость Низкая (стандартные функции). Очень высокая. Плагины подгружаются прямо в ядро (поддерживается безопасный список расширений в Azure).
Бизнес-применение Быстрые веб-сайты (WordPress, Magento), каталоги, простые транзакции. Сложная бизнес-логика, гео-отслеживание такси (PostGIS), финансовая аналитика, ERP-системы.
Компромисс (Минус) Плохо справляется с тяжелой аналитикой и сложными JOIN. Более высокое потребление памяти на каждое подключение; сложнее в администрировании.

Модуль 3. Практика: Развертывание (Provisioning) и защита периметра

TL;DR: Развертывание (Provisioning) БД в облаке — это процесс выделения ресурсов. В Azure он состоит из 3 шагов: создание Логического сервера (управляет логинами и сетью), создание Самой базы (хранит таблицы) и настройка Сетевого экрана / Firewall (решает, кто может подключиться).

Под капотом (Deep Dive): Механика развертывания шаг за шагом

Когда вы нажимаете "Create" в Azure Portal, выстраивается следующая иерархия:

  1. Resource Group (Группа ресурсов): Это папка (логический контейнер). В неё складывается сервер, база, бэкапы. Главное правило: удаление Resource Group мгновенно удаляет все внутри и гарантированно останавливает списание денег (важно для тренировок и лаб).
  2. Logical Server (Логический сервер SQL): В отличие от локального сервера, это не виртуальная машина, на которую можно зайти по RDP. Это просто URL-адрес (например, myserver.database.windows.net) и контроллер политик безопасности (кто имеет права админа).
  3. Authentication (Аутентификация): Как мы будем подключаться?
    • SQL Auth: Старые добрые логин и пароль. (Быстро, но менее безопасно).
    • Microsoft Entra ID (ранее Azure AD): Вход по корпоративной учетной записи. Это более безопасно (Best Practice), так как поддерживает многофакторную аутентификацию (MFA).
Best Practices vs. Anti-patterns (Настройка Сети):

База в облаке по умолчанию заблокирована для всего интернета. Как к ней подключиться?

✔ Правильно (Best Practice): Использовать Private Endpoints (Закрытые конечные точки). База получает внутренний IP-адрес вашей корпоративной сети. Хакеры из интернета физически не видят вашу базу.
Архитектурный лимит: логический сервер SQL поддерживает максимум 250 частных конечных точек (Private Endpoints).

⚠ Допустимо (Для разработки): Открыть Firewall строго для вашего текущего IP-адреса (настройка Add current client IP).

✖ Неправильно (Anti-pattern): Включать опцию Allow Azure services and resources to access this server в продакшене. Эта настройка разрешает доступ к вашей базе с ЛЮБОГО ресурса Azure (включая чужие виртуалки, купленные злоумышленниками в их собственных аккаунтах Azure).

Пример: Создание реляционной связи (DDL)

Создание двух таблиц с жесткой ссылочной целостностью:

CREATE TABLE Manufacturer (
    ManufacturerID INT PRIMARY KEY,
    ManufacturerName NVARCHAR(50) NOT NULL
);

CREATE TABLE Vehicle (
    VehicleID INT PRIMARY KEY,
    ManufacturerID INT NOT NULL,
    ListPrice DECIMAL(10, 2),
    FOREIGN KEY (ManufacturerID) REFERENCES Manufacturer(ManufacturerID)
);

Объяснение: СУБД физически запретит добавить автомобиль (Vehicle), если его ManufacturerID не существует в таблице Manufacturer.

Модуль 4. Оценка модуля (Проверка знаний)

Архитектурный разбор тестовых заданий

Ниже представлены правильные ответы на вопросы оценки с техническим обоснованием каждого выбора.

  1. Какой сервис Azure SQL вы бы использовали для среды разработки, где требуется быстрое создание и удаление экземпляров?
    ✔ База данных SQL Azure
    Обоснование: Это чистый PaaS. Развертывание и удаление занимает считанные минуты, что идеально подходит для временных Dev/Test сред.
  2. Какая служба SQL Azure лучше всего подходит для сценария, в котором необходимо легко управлять эластичностью базы данных и выделением ресурсов в нескольких базах данных?
    ✔ База данных SQL Azure с эластичным пулом (Elastic Pool)
    Обоснование: Эластичные пулы позволяют множеству баз данных делить между собой общий пул вычислительных ресурсов (vCore/DTU), что сильно экономит бюджет при неравномерных нагрузках (SaaS-приложения).
  3. Компания планирует перенести свою базу данных MySQL в Azure для повышения масштабируемости и автоматического резервного копирования. Какую службу Azure следует выбрать?
    ✔ База данных Azure для MySQL
    Обоснование: Прямой переход на нативный PaaS-сервис от Azure для MySQL обеспечит и масштабируемость, и встроенные бэкапы без изменения кода приложения.
  4. Для организации требуется решение базы данных, поддерживающее модель гибридного развертывания, что позволяет легко интегрироваться с локальными системами. Какую службу SQL Azure следует выбрать?
    ✔ SQL Server на Виртуальных машинах Microsoft Azure
    Обоснование: IaaS-модель (виртуальные машины) обеспечивает 100% сетевую и инфраструктурную совместимость для интеграции с локальными (on-premises) доменами Active Directory и построения гибридных кластеров AlwaysOn.
  5. Компания должна перенести базу данных в облако с минимальными изменениями в существующих приложениях и требует таких функций, как связанные серверы (Linked Servers) и Service Broker. Какую службу следует выбрать?
    ✔ Управляемый экземпляр SQL Azure (Managed Instance)
    Обоснование: Managed Instance создан специально для бесшовной миграции "Lift-and-Shift". Он поддерживает старые фичи уровня инстанса (Linked Servers, SQL Agent, Service Broker), которых нет в обычной "Базе данных SQL Azure".
  6. Ваша организация хочет перенести локальную базу данных SQL Server в Azure. База данных имеет сложные запросы и требует полных прав администратора по СУБД и операционной системе. Какая служба SQL Azure лучше всего соответствует этим требованиям?
    ✔ SQL Server на Виртуальных машинах Microsoft Azure
    Обоснование: Ключевая фраза — "требует полных прав на операционную систему". Только IaaS дает доступ по RDP к самой Windows/Linux.
  7. Компания обеспокоена административными расходами на управление обновлениями и резервными копиями базы данных. Они рассматривают миграцию рабочих нагрузок SQL Server в Azure. Какая служба Azure SQL поможет свести к минимуму их административные задачи?
    ✔ Управляемый экземпляр SQL Azure (Managed Instance)
    Обоснование: Если мигрируются "существующие рабочие нагрузки SQL Server" с целью превратить их в PaaS (убрать рутину управления бэкапами и патчами), Managed Instance — лучший выбор, так как не требует переписывания кода, в отличие от Azure SQL Database.
  8. Ваша компания должна обеспечить высокий уровень доступности и автоматические обновления для решения облачной базы данных. Какая служба Azure SQL предлагает доступность 99.995% и автоматическое управление?
    ✔ База данных SQL Azure
    Обоснование: База данных SQL Azure на уровне Business Critical / Premium (с резервированием зон) гарантирует самый высокий на рынке SLA (99.995%) и является полностью управляемым PaaS-решением.
  9. Технологическая компания нуждается в масштабируемом решении базы данных для своего нового облачного приложения, которое сводит к минимуму затраты и административные усилия. Они ожидают нагрузки переменных и требуют быстрого масштабирования. Какая служба SQL Azure наиболее подходит?
    ✔ База данных SQL Azure с бессерверной конфигурацией (Serverless)
    Обоснование: Ключевые слова "новое облачное приложение", "переменные нагрузки" и "минимизация затрат". Бессерверная конфигурация (Serverless) автоматически масштабирует вычислительную мощность посекундно и может ставить базу "на паузу" при отсутствии активности, экономя деньги.
