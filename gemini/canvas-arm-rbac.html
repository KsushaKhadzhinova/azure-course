Архитектурный конспект: Управление ресурсами и безопасность в Azure (ARM & RBAC)

TL;DR: Для создания любой облачной инфраструктуры вам нужен координатор и охранник. В Azure координатором выступает Azure Resource Manager (ARM) — единый уровень управления и развертывания (IaC). Охранником работает Azure RBAC в связке с Microsoft Entra ID.

Модуль 1. Azure Resource Manager и Поставщики ресурсов

Рис 1. ARM выступает как единая "воронка" (шлюз). Действие в Portal, скрипт в CLI или вызов REST API дают абсолютно идентичный результат.

Архитектурный фундамент: Плоскость управления (Control Plane) vs Плоскость данных (Data Plane)

Плоскость управления (Control Plane) Плоскость данных (Data Plane)
Управляет: Созданием, удалением и настройкой самих ресурсов (создать ВМ, базу данных). Управляет: Работой с данными внутри ресурса (чтение таблиц, загрузка файлов, RDP на виртуалку).
Глобальный URL: https://management.azure.com Локальный URL: Уникален для ресурса (например, https://myaccount.blob.core.windows.net).
Ограничения: Политики Azure, Блокировки ресурсов (Locks) и ARM RBAC. Ограничения: Собственные механизмы БД, ключи доступа или Data Plane RBAC.

Главное правило отказоустойчивости: Даже если глобальный портал Azure временно недоступен, ваши приложения продолжат работу! Они общаются с базами напрямую через Data Plane.

Поставщики ресурсов (Resource Providers)

Каждая служба Azure работает через своего поставщика. Например, хранилище ключей — это Microsoft.KeyVault, а ВМ — Microsoft.Compute.

Best Practice: Принцип наименьших привилегий для Провайдеров

Не регистрируйте поставщиков ресурсов "на всякий случай". При регистрации некоторых провайдеров (например, через Windows Azure Service Management API) в вашем тенанте Microsoft Entra автоматически создаются служебные Enterprise-приложения. Злоумышленник не может использовать незарегистрированного поставщика для создания скрытых ресурсов (криптомайнеров) в вашей подписке.

Защита инфраструктуры: Блокировки ресурсов (Resource Locks)

Блокировки применяются ТОЛЬКО к плоскости управления (Control Plane):

  • CanNotDelete: Ресурс можно читать и изменять, но нельзя удалить.
  • ReadOnly: Ресурс можно только читать (любые POST/PUT запросы уровня управления блокируются).

Побочные эффекты ReadOnly: Вы не сможете посмотреть ключи доступа Storage Account на портале, так как портал делает POST запрос (Control Plane) для получения ключей. При этом само приложение, если у него уже есть ключ, продолжит писать данные (Data Plane).

Архитектура Групп Управления (Management Groups)

  • Масштаб: Один тенант (Microsoft Entra ID) может содержать до 10 000 групп управления.
  • Корневая группа (Root Management Group): В нее автоматически падают все новые подписки. Назначение политики (например, запрет регионов) на этот уровень влияет на всю корпорацию. Идентификатор группы совпадает с Tenant ID.

Механика перемещения и удаления ресурсов

Перенос ресурсов (Resource Mover) — сложный процесс:

  • Во время перемещения и исходная, и целевая Группы ресурсов блокируются на срок до 4 часов.
  • Ресурс переносится только вместе с зависимостями (частая ошибка MissingMoveDependentResources).
  • Назначения ролей (RBAC) НЕ перемещаются и становятся осиротевшими.
  • При удалении РГ (Resource Group), Resource Manager сначала удаляет дочерние элементы, затем управляющие ресурсы (с флагом managedBy), а в конце — независимые. Удаление необратимо.

Модуль 3. Инфраструктура как код (Bicep) и Кросс-уровневые деплои

Эволюция IaC: ARM JSON → Bicep

Bicep — это предметно-ориентированный язык, который транслируется в ARM JSON, но избавляет инженера от "скобочного ада". Преимущества: автоматическое разрешение dependsOn, отсутствие "стейт-файлов" (в отличие от Terraform, состояние хранит сам Azure) и интеграция с операцией What-If.

Кросс-уровневые развертывания (Cross-Scope Deployments)

IaC позволяет разворачивать инфраструктуру не только внутри Resource Group, но и на более высоких уровнях:

  • Subscription Scope: Позволяет автоматизировать создание самих Resource Groups и политик. (Например, az deployment sub create).
  • Management Group Scope: Позволяет применить Azure Policy или назначить роли RBAC сразу на сотни подписок внутри группы.
  • Tenant Scope: Используется для глобального назначения ролей. (Требует роли Owner в корне).

Модуль 4. Microsoft Entra ID, Роли и Условия (Azure ABAC)

Главная путаница новичков — разница между ролями Azure и Entra ID.

  • Роли Azure (Azure RBAC): Управляют ресурсами (ВМ, базы, сети). Пример: Virtual Machine Contributor.
  • Роли Microsoft Entra: Управляют пользователями, лицензиями и паролями в каталоге. Пример: Global Administrator, User Administrator.

Секрет: Global Administrator по умолчанию НЕ имеет доступа к ресурсам Azure. Но он может воспользоваться кнопкой "Эскалация прав" (Elevate Access), чтобы временно выдать себе роль User Access Administrator на уровне Root Scope (/), подчинив себе все подписки.

Анатомия пользовательских ролей (Custom Roles)

Каждый тенант поддерживает до 5000 кастомных ролей. Определение роли состоит из массивов:

  • Actions / NotActions — Управление плоскостью управления (Control Plane).
  • DataActions / NotDataActions — Управление плоскостью данных (Data Plane).
  • AssignableScopes — Где эта роль может быть назначена (не используйте корень / для кастомных ролей!).

Математика вычисления эффективных прав

Доступ по RBAC вычисляется по формуле: Actions - NotActions = Эффективные права. Если у вас две роли (одна разрешает, другая использует NotActions), то разрешение побеждает (NotActions не является жестким запретом).

Однако, Запреты назначений (Deny Assignments), которые создаются системой (например, Azure Blueprints), имеют наивысший приоритет и блокируют доступ вне зависимости от выданных ролей.

Azure ABAC (Attribute-Based Access Control)

Иногда обычного RBAC недостаточно. Azure ABAC добавляет Условия (Conditions) к назначениям ролей. Это помогает кардинально снизить количество выдаваемых ролей (лимит: 5000 на подписку).


(
  !(ActionMatches{'Microsoft.Storage/storageAccounts/.../blobs/read'})
)
OR
(
  @Resource[.../blobs/tags:Project] StringEqualsIgnoreCase 'Cascade'
)
Пример ABAC: Пользователь может читать только те Blob-объекты, на которых висит тег Project=Cascade.

Интеграция с PIM (Privileged Identity Management)

При наличии лицензии Entra ID P2, вы можете назначать роли не навсегда, а по принципу JIT (Just-In-Time):

  • Active (Активные): Роль назначена и работает сразу (может быть постоянной или ограниченной по времени).
  • Eligible (Допустимые/По запросу): Пользователь должен явно "активировать" роль. Во время активации может потребоваться ввод MFA, бизнес-обоснование или согласование от менеджера.
Ограниченное делегирование прав (Constrained Delegation)

Не выдавайте пользователям роль Owner или User Access Administrator, чтобы они могли раздавать права другим! Они смогут выдать права кому угодно, включая себя.

Вместо этого используйте роль Role Based Access Control Administrator в связке с Условиями (ABAC). Например, вы можете задать условие: "Этот тимлид может назначать только роль 'Backup Reader' и только участникам группы 'Marketing'".

Сводка и Итоги

Управление ресурсами и безопасность — это основа надежной облачной архитектуры.

  • Архитектура: Строгое разделение Control Plane (управление) и Data Plane (данные). Понимание того, как Resource Locks блокируют портал, но не останавливают транзакции.
  • Масштаб и Лимиты: Управление тысячами подписок через Management Groups, понимание 4-часовых блокировок при перемещении (Resource Mover) и лимитов в 800 ресурсов на группу.
  • IaC (Bicep): Возможность разворачивать инфраструктуру (политики, РГ) не только на уровне ресурсов, но и на уровне подписок и тенантов.
  • Безопасность (RBAC, ABAC, PIM): Математика вычисления прав (Actions - NotActions), использование тегов для фильтрации доступа к блобам (ABAC) и защита привилегированных учеток через временную активацию ролей (PIM / Eligible assignments).
