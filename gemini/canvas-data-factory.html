Архитектурный конспект: Azure Data Factory (ADF)

TL;DR: Azure Data Factory (ADF) — это управляемый облачный PaaS-сервис для оркестрации и автоматизации перемещения и преобразования данных в масштабах предприятия (гибридные проекты ETL и ELT). Он поддерживает более 100 встроенных коннекторов, предлагает визуальный no-code/low-code интерфейс, запускает трансформации на управляемых кластерах Spark (Mapping Data Flows) и бесшовно интегрируется с Azure Synapse, Databricks и Power BI.

Эволюция платформы (Microsoft Fabric): Data Factory в Microsoft Fabric — это следующее поколение Azure Data Factory (SaaS) с упрощенной архитектурой, встроенным ИИ (Copilot) и единым хранилищем OneLake. Если вы начинаете проект с нуля, Microsoft рекомендует стартовать с Fabric Data Factory, однако знания и навыки ADF переносятся туда практически 1-в-1.

Аналогия из жизни (Автоматизированный логистический хаб):

Представьте, что ваши данные разбросаны по десяткам складов (локальный SQL Server, облачные хранилища Amazon S3, REST API, файлы Excel). Azure Data Factory — это не сам склад и не магазин, а диспетчерский центр и конвейерная лента. Он сам отправляет грузовики (Copy Activity) по расписанию или по сигналу (Trigger), переупаковывает и сортирует груз на фабрике (Data Flows / Spark) и доставляет готовые паллеты в витрину для аналитиков (Synapse / Power BI).

Модуль 1. Архитектура, возможности и 4 этапа работы ADF

В мире больших данных сырые, неорганизованные данные сами по себе не несут бизнес-ценности. Azure Data Factory превращает их в аналитические активы через 4 взаимосвязанных этапа:

Рис 1. Пять столпов Code-Free ETL как сервиса в Azure Data Factory: Прием (Ingest), Поток управления (Control Flow), Потоки данных (Data Flow), Расписание (Schedule) и Мониторинг (Monitor).
  1. Подключение и сбор (Connect & Collect): Подключение к разнородным локальным, облачным и SaaS-источникам (100+ коннекторов) и перенос данных в централизованное облачное хранилище (например, ADLS Gen2) с помощью Copy Activity. Поддерживается сжатие данных (Data Compression) для экономии сетевого трафика и предпросмотр/валидация (Data Preview & Validation).
  2. Преобразование и обогащение (Transform & Enrich): Очистка, объединение (Joins), агрегация и обогащение данных. Можно делать без кода через Mapping Data Flows (работают на управляемых кластерах Spark) или вызывать внешние вычисления (Azure Databricks, HDInsight Hadoop, Azure Machine Learning).
  3. CI/CD и публикация (CI/CD & Publish): Полноценная интеграция с Git (Azure DevOps и GitHub) позволяет разрабатывать пайплайны в ветках, тестировать и выкатывать релизы в продакшн. Очищенные данные загружаются в Azure Synapse Analytics, Azure SQL или Cosmos DB для отчетов Power BI.
  4. Мониторинг (Monitor): Встроенное отслеживание успешности и сбоев запусков через вкладку Monitor, Azure Monitor, Log Analytics, PowerShell и настраиваемые оповещения (Alerts).

Классический Enterprise-сценарий (Игровая студия)

Задача: Игровая компания собирает петабайты логов в облаке (Blob Storage), а справочники игроков, игр и маркетинговых кампаний хранятся в локальной БД (on-premises). Нужно ежедневно (и при появлении новых файлов) объединять эти данные, обрабатывать в Spark и отдавать в хранилище для BI-отчетов.

Решение в ADF:

  • Через Self-Hosted Integration Runtime безопасно забираются справочники из локальной сети.
  • Конвейер (Pipeline) объединяет их с облачными логами и передает на кластер Spark (Databricks / HDInsight).
  • Результат публикуется в Azure Synapse Analytics для дашбордов Power BI.
  • Автоматизация обеспечивается комбинацией триггера по расписанию и событийного триггера (Blob Arrival).

Компонент Роль и Суть Примеры / Особенности
Pipeline (Конвейер) Логическая группировка активностей, выполняющая единую бизнес-задачу. Активности могут идти последовательно (цепочкой) или параллельно. Управляется как единое целое.
Activity (Активность) Конкретный шаг обработки внутри конвейера. Делятся на 3 типа: Data Movement (Copy), Data Transformation (Data Flow, Databricks Notebook, Hive, Stored Proc) и Control Flow (ForEach, If Condition, Switch, Wait).
Dataset (Набор данных) Именованное представление структуры данных (указатель на конкретную таблицу или папку). Например, CSV-файл в контейнере Blob или таблица dbo.Sales в Azure SQL. Определяет схему и формат (Parquet, JSON, CSV).
Linked Service (Связанная служба) Аналог строки подключения (Connection String) к внешнему ресурсу. Используется для 2 целей: подключение к хранилищам данных (SQL, S3, ADLS) и к вычислительным ресурсам (Databricks, HDInsight).
Mapping Data Flows Визуальный граф трансформаций данных любого объема без написания кода. ADF сам поднимает, масштабирует и гасит кластеры Apache Spark под капотом. Поддерживает Join, Aggregate, Derived Column, Filter, Delta Lake.
Triggers & Pipeline Runs Trigger определяет, когда запустить конвейер. Pipeline Run — это конкретный экземпляр запуска. Типы триггеров: Schedule (расписание), Tumbling Window (скользящие окна), Storage Events (появление/удаление файла), Custom Events (Event Grid).
Parameters vs Variables Механизмы динамической настройки конвейеров. Parameters — неизменяемые (read-only) пары ключ-значение, передаваемые при запуске. Variables — изменяемые временные значения внутри работающего конвейера.

Типы сред выполнения (Integration Runtimes — IR)

Integration Runtime (IR) — это вычислительный мост между активностью и связанной службой. Выбор правильного IR критически важен для безопасности, сетевой связности и производительности:

Тип IR Где работает Возможности и Сценарии применения
Azure IR Полностью управляется Microsoft в облаке Azure. Облачные копирования (Cloud-to-Cloud), выполнение Mapping Data Flows, отправка задач в облачные вычислители. Поддерживает Managed Virtual Network и Private Endpoints.
Self-Hosted IR (SHIR) Устанавливается как агент на вашей Windows-машине (on-premises или в частной VNet). Гибридные сценарии: безопасное копирование данных из локального SQL Server / файловых шар за корпоративным брандмауэром в облако Azure без открытия входящих портов.
Azure-SSIS IR Управляемый кластер виртуальных машин Azure. Миграция «Lift-and-Shift» для запуска существующих пакетов SQL Server Integration Services (SSIS) напрямую в облаке.

Модуль 3. Практика: Сборка первого конвейера в ADF Studio

Интерфейс Azure Data Factory Studio разделен на три ключевые рабочие области (слева в меню):

  • Author (Создание): Визуальный редактор конвейеров, датасетов и потоков данных.
  • Monitor (Мониторинг): История запусков (Pipeline/Trigger Runs), диагностика ошибок и статус IR.
  • Manage (Управление): Настройка Linked Services, Integration Runtimes, Git-репозиториев и триггеров.

Пошаговый чек-лист сборки (Blob Storage → Azure SQL)

  1. Создайте Linked Services (вкладка Manage): Добавьте подключение к источнику (Azure Blob Storage) и приемнику (Azure SQL Database). Предпочтительный метод аутентификации — Managed Identity. Обязательно нажмите Test connection.
  2. Создайте Datasets (вкладка Author): Создайте два набора данных (например, DelimitedText для CSV и AzureSqlTable для целевой таблицы), привязав их к соответствующим Linked Services, и импортируйте схему (Import schema).
  3. Настройте Copy Data Activity: Создайте новый Pipeline, перетащите на холст Copy data. На вкладке Source выберите исходный датасет, на Sink — целевой, а на вкладке Mapping проверьте соответствие столбцов и типов данных.
  4. Опубликуйте и запустите (Publish & Trigger): Нажмите Publish all (без публикации изменения остаются черновиком и не запускаются триггерами!). Для проверки нажмите Add trigger → Trigger now и отследите выполнение во вкладке Monitor.

Модуль 4. Выбор архитектуры: Azure Data Factory vs Microsoft Fabric

Критерий Azure Data Factory (ADF) Microsoft Fabric Data Factory
Модель доставки Автономный PaaS-сервис в Azure. Единая SaaS-платформа (Data Factory + Synapse + Power BI).
Хранилище Работает через Linked Services с любыми внешними хранилищами. Глубокая нативная интеграция с OneLake (Zero-Copy Shortcuts, Mirroring).
Инфраструктура и ИИ Гранулярный контроль над IR, сетями и ресурсами. Упрощенная архитектура, встроенный Copilot (ИИ), быстрый старт.
Когда выбирать? Зрелые Enterprise-проекты, сложные гибридные сети с legacy on-premises системами, жесткий контроль над выделенными IR и SSIS-пакетами. Новые современные платформы данных, где инженерия, хранилище, Real-Time аналитика и Power BI должны жить в едином рабочем пространстве.

Модуль 5. Архитектурные Best Practices и Безопасность

✔ Правильно (Best Practices):
  • Модульность и параметризация: Вместо 50 одинаковых пайплайнов для 50 таблиц создайте один параметризованный конвейер с циклом ForEach и таблицей метаданных (Metadata-Driven Pipeline).
  • Сжатие данных (Compression): Включайте сжатие (например, gzip) в Copy Activity при переносе больших объемов данных для ускорения передачи и экономии трафика.
  • Политики повторов (Retry Policies): Настраивайте автоматические ретраи для защиты от кратковременных сетевых сбоев (transient errors) и подключайте оповещения Azure Monitor.
  • Безопасность (Zero Trust): Используйте Managed Identity (Entra ID) + Azure Key Vault для секретов, а также Managed Virtual Network с Private Endpoints против утечки данных.
  • Инкрементальная загрузка (CDC / Watermark): Загружайте только новые или измененные строки (через Change Tracking / CDC), а не копируйте всю базу целиком каждый день.
✖ Неправильно (Anti-patterns):
  • Использовать Mapping Data Flows для простого копирования: Data Flows поднимают кластер Spark (время старта + высокая цена). Если трансформация не нужна, используйте быстрый и дешевый Copy Activity.
  • Хардкодить пароли и пути: Никогда не вшивайте строки подключения в JSON пайплайна и не дублируйте датасеты для каждого файла — используйте параметры и Key Vault.
  • Разрабатывать напрямую в Live Mode: Работа без подключения Git-репозитория (Azure DevOps / GitHub) лишает команду версионирования, Code Review и возможности отката изменений.
  • Игнорировать выбор региона IR: Размещение Azure IR далеко от источника и приемника вызывает лишнюю сетевую задержку и плату за межрегиональный трафик (Egress).
