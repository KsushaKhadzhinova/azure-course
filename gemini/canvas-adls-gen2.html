Архитектурный конспект: Общие сведения об Azure Data Lake Storage 2-го поколения

TL;DR: Azure Data Lake Storage (ADLS) 2-го поколения — это не отдельный сервис, а набор возможностей для аналитики больших данных, встроенный поверх стандартного хранилища BLOB-объектов Azure. Включив одну галочку (Иерархическое пространство имен), вы превращаете дешевое хранилище объектов в сверхпроизводительную распределенную файловую систему, совместимую с Apache Hadoop и Spark.

Модуль 1. Проблема реляционных хранилищ и появление Озер Данных

На протяжении двух десятилетий организации строили свои решения бизнес-аналитики (BI) на базе Хранилищ данных (Data Warehouses). Реляционные БД отлично подходили для структурированных транзакций, но с развитием технологий они столкнулись с фундаментальной проблемой.

Ограничения Data Warehouse:

  • Высокая стоимость: Хранить петабайты сырых логов и JSON в реляционной базе невероятно дорого (вы платите за мощный CPU и быстрые диски, даже если данные просто лежат).
  • Сложность (Schema-on-write): Чтобы записать данные в реляционное хранилище, их сначала нужно очистить и подогнать под строгую структуру таблиц. Неструктурированные данные (картинки, видео, свободный текст) хранить там невозможно.

Решение — Data Lake (Озеро данных): Распределенная файловая система, которая позволяет сбрасывать данные в их исходном "сыром" виде. Озера оптимизированы для масштабирования до петабайт данных и используются движками больших данных (например, Apache Spark) для анализа.

Модуль 2. Что такое ADLS Gen2 и как его включить?

Под капотом (Deep Dive): Включение ADLS Gen2

Архитектурно Azure Data Lake Storage 2-го поколения — это Хранилище BLOB-объектов Azure + Иерархическое пространство имен (HNS). Это не автономная служба, а надстройка (возможность).

Ее можно включить для учетных записей:

  • Общего назначения уровня "Стандартный" v2 (GPv2) — наиболее распространенный и экономичный вариант.
  • Блочного BLOB-объекта класса Premium — для рабочих нагрузок, критичных к задержкам и требующих максимальной пропускной способности.
Рис 1. При создании учетной записи хранения на вкладке "Дополнительно" необходимо активировать чекбокс «Включить иерархическое пространство имен».

Миграция существующих учетных записей

Если у вас уже есть стандартное хранилище Blob (с плоским пространством имен), вы можете обновить его до ADLS Gen2 прямо на портале Azure через меню «Data Lake Gen2 upgrade».

Рис 2. Процесс апгрейда существующей учетной записи. Во время обновления хранилище будет находиться в автономном режиме.
Архитектурное предупреждение:
✔ Правильно (Best Practice): Включать HNS в момент создания учетной записи хранения для аналитических нагрузок.
✖ Критический нюанс: Процесс обновления существующего хранилища через портал является односторонним (необратимым). Вы не сможете вернуть учетную запись обратно в плоское пространство имен после завершения миграции!

Модуль 4. Сравнение Azure Blob Storage и ADLS Gen2

Почему для аналитики недостаточно обычного хранилища Blob? Все дело в управлении папками и метаданными.

Рис 4. Плоское пространство (Blob Storage). Папки folder1 не существует. Имя файла — folder1/blob2.
Рис 5. Иерархическое пространство (ADLS Gen2). Папка Directory является физическим объектом с метаданными.
Характеристика Azure Blob Storage (Обычное) ADLS Gen2 (С включенным HNS)
Структура Плоское пространство имен (Flat). Папок не существует физически, это просто часть имени файла. Иерархическое пространство имен (HNS). Папки являются реальными объектами первого класса (сохраняют метаданные о файлах внутри).
Производительность (Переименование/Удаление папок) Требует выполнения нескольких операций, число которых пропорционально количеству объектов внутри. Одна атомарная операция. Изменяется только метаданные самой папки. Критически снижает стоимость анализа для Big Data.
Безопасность (Доступ) RBAC применяется на уровне всего контейнера. POSIX ACLs: Можно задать детальные права доступа на конкретную папку или даже отдельный файл внутри озера.
Драйвер Hadoop wasb:// abfs:// (Azure Blob File System) — приложения могут обращаться как через Blob API, так и через Data Lake API.

Когда НЕ нужно включать HNS?

Если вы хотите хранить данные без выполнения анализа, оставьте параметр «Включить иерархическое пространство имен» очищенным. Обычное хранилище BLOB-объектов идеально подходит для:

  • Архивации редко используемых данных (Archive tier).
  • Хранения ресурсов статических веб-сайтов (изображения, аудио, CSS, скрипты).
  • Хранения дисков виртуальных машин (Page Blobs).

Модуль 5. ADLS Gen2 в этапах аналитической обработки

Озеро данных является центральным элементом классического конвейера больших данных. Любая архитектура работы с данными (Хранилище корпоративных данных, Аналитика в реальном времени, Машинное обучение) включает четыре фундаментальных стадии:

flowchart LR A[1. Прием \n Ingest] -->|Сырые данные| B[(2. Хранение \n Store)] B -->|Очистка и Обучение| C{3. Подготовка \n Prep & Train} C -->|Бизнес-логика| D[4. Моделирование \n Model & Serve] style B fill:#AED6F1,stroke:#3498DB,stroke-width:2px
Рис 6. Четыре стадии обработки больших данных. ADLS Gen2 выступает надежным слоем Хранения (Store).
  1. Прием (Ingest): Технологии для получения исходных данных (логов, файлов). Для пакетного приема (раз в сутки) используются конвейеры Microsoft Fabric или Azure Data Factory. Для потокового (в реальном времени) — Event Hubs или Stream Analytics.
  2. Хранение (Store): Azure Data Lake Storage 2-го поколения принимает все эти потоки данных. Он предоставляет масштабируемое решение, совместимое с форматами Big Data (Parquet, Delta Lake).
  3. Подготовка и обучение (Prep & Train): Распределенные системы (Azure Databricks, Fabric Spark) читают данные из озера, очищают их и используют для обучения ИИ-моделей (в Azure Machine Learning).
  4. Моделирование и Предоставление (Model & Serve): Очищенные данные подаются конечным пользователям через Azure Synapse Analytics или напрямую в дашборды Microsoft Power BI.

Модуль 6. Использование ADLS Gen2 в аналитических рабочих нагрузках

Рассмотрим, как именно ADLS Gen2 взаимодействует с другими сервисами Azure в реальных бизнес-сценариях.

Сценарий 1: Хранение данных (Data Warehousing / ETL)

Данные извлекаются из операционных баз (Azure SQL, Cosmos DB) и помещаются в ADLS Gen2. Затем они обрабатываются и загружаются в реляционное хранилище данных (например, Azure Synapse) для отчетности.

Рис 7. Конвейер: Операционная БД -> Azure Data Factory (ETL) -> ADLS Gen2 -> Azure Synapse Analytics -> Power BI.

Сценарий 2: Аналитика в реальном времени (Real-Time Analytics)

Непрерывные потоки данных (от датчиков IoT или соцсетей) фиксируются в очередях и обрабатываются без задержек. ADLS Gen2 выступает в роли "приемника" (sink) для сохранения истории этих потоков.

Рис 8. Конвейер: Потоковые данные -> Azure Event Hubs (Очередь) -> Azure Stream Analytics (Агрегация) -> ADLS Gen2 (Приемник).

Сценарий 3: Обработка, анализ данных и Машинное обучение (Data Science & ML)

Обучение ИИ-моделей требует огромных объемов сырых данных. Специалисты по Data Science подключают кластеры вычислений напрямую к Озеру данных для тренировки прогнозных моделей.

Рис 9. Конвейер: ADLS Gen2 (Сырые данные) -> Загрузка в Azure Machine Learning (Python/Jupyter) -> Обученная модель.
