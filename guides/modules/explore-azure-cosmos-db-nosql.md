# Знакомство с Azure Cosmos DB for NoSQL

**Источник:** https://learn.microsoft.com/en-us/training/modules/explore-azure-cosmos-db-nosql/

## Цель модуля

Научиться оценивать, подходит ли Azure Cosmos DB for NoSQL для конкретной нагрузки, понимать модель данных (аккаунт, база данных, контейнер, элемент), три механизма масштабирования (request units, партиционирование, глобальное распределение) и базовые операции в Data Explorer.

## Ключевые понятия

- **Azure Cosmos DB for NoSQL** - полностью управляемая NoSQL- и векторная база данных, которая хранит JSON-документы без заранее заданной схемы.
- **Account (аккаунт)** - верхний ресурс: задает регионы, DNS-имя для API и настройки уровня аккаунта, например уровень согласованности по умолчанию. API выбирается при создании и не меняется.
- **Database (база данных)** - логическая единица управления, группирующая контейнеры.
- **Container (контейнер)** - основная единица масштабирования; на нем обычно задается throughput, индексная политика и TTL.
- **Item (элемент)** - отдельный JSON-документ в контейнере; элементы одного контейнера могут различаться по структуре. Запись одного элемента атомарна.
- **Request unit (RU)** - нормализованная единица стоимости операции. Точечное чтение элемента 1 KB по id и partition key стоит 1 RU.
- **Logical partition (логическая партиция)** - все элементы с одним значением partition key; лимит - 20 GB на логическую партицию.
- **Physical partition (физическая партиция)** - управляемая сервисом единица вычислений и хранения; до 10 000 RU/s и до 50 GB данных. Пользователь ее не создает.
- **Partition key (ключ партиционирования)** - свойство элемента, определяющее логическую партицию; меняется только копированием данных в новый контейнер.
- **Global distribution (глобальное распределение)** - репликация данных аккаунта в любое число регионов; режимы single-region writes и multi-region writes.
- **Autoscale** - автоматическое изменение throughput между 10% и 100% заданного максимума без разрыва соединений.
- **Consistency levels (уровни согласованности)** - пять уровней от самого строгого к самому слабому: strong, bounded staleness, session, consistent prefix, eventual.
- **Hierarchical partition keys (иерархические ключи)** - подпартиционирование до трех уровней ключей для больших значений ключа, например крупных арендаторов.
- **Data Explorer** - инструмент портала Azure для создания ресурсов, просмотра данных и выполнения запросов без кода.
- **Change feed (лента изменений)** - обработка вставок и обновлений; упомянута как возможность сервиса.

## Содержание по урокам

### 1. Введение
Источник: https://learn.microsoft.com/en-us/training/modules/explore-azure-cosmos-db-nosql/1-introduction

Сценарий: интернет-магазин Contoso переписывает каталог с реляционной БД. Требования: быстрый доступ по всему миру, гибкая схема, масштабирование throughput под распродажи и хранение векторных эмбеддингов рядом с данными о товарах. Azure Cosmos DB for NoSQL закрывает эти требования; модуль помогает принять решение и понять механику.

### 2. Что такое Azure Cosmos DB for NoSQL
Источник: https://learn.microsoft.com/en-us/training/modules/explore-azure-cosmos-db-nosql/2-what-is-azure-cosmos-db-nosql

- NoSQL-базы обычно хранят данные в нереляционном формате, масштабируются горизонтально и не требуют фиксированной схемы. Azure Cosmos DB for NoSQL использует модель документов с JSON.
- Ресурсы: аккаунт, база данных, контейнер и элемент. Элемент - самодостаточный JSON-документ с полем `id`; запрос выполняется ровно к одному контейнеру.
- Разработка: SDK для .NET, Java, Python, JavaScript/Node.js, Go и Rust; транзакционные батчи для элементов с одним логическим ключом, change feed, векторный индекс, полнотекстовый и гибридный поиск.
- Ключевые характеристики: глобальное распределение (регионы можно добавлять онлайн); эластичное масштабирование (autoscale, без ограничения общего размера контейнера, до 20 GB на логическую партицию); низкая задержка (чтение одного элемента и индексированная запись менее 10 мс на 99-м перцентиле по SLA; исключение - запись в мульти-регион с strong согласованностью); настраиваемая согласованность из пяти уровней.
- По умолчанию индексируются все свойства всех элементов; индексную политику можно сузить позднее для снижения стоимости.

### 3. Как работает Azure Cosmos DB for NoSQL
Источник: https://learn.microsoft.com/en-us/training/modules/explore-azure-cosmos-db-nosql/3-how-azure-cosmos-db-nosql-works

- **Request units**: каждая операция (чтение, запись, запрос) выражается в RU. Базовая точка отсчета - точечное чтение 1 KB элемента = 1 RU; запись дороже чтения, большие элементы и сканирующие запросы дороже еще больше. Throughput задается в RU/s. Это дает предсказуемость (стоимость известна) и эластичность (RU/s можно менять).
- **Партиционирование**: логическая партиция - все элементы с одним значением partition key; физическая партиция - единица сервиса (до 10 000 RU/s и 50 GB). Azure Cosmos DB хеширует значения ключа и сама делит физические партиции. Хорошая аналогия из модуля: логические партиции - ярлыки папок, физические - шкафы.
- Ключ определяет равномерность распределения: ключ с малым числом значений ведет к горячим партициям. Запрос с одним значением ключа идет в одну логическую партицию; без ключа может обращаться ко всем физическим партициям.
- Для данных больше 20 GB на одно значение ключа используются иерархические ключи (до трех уровней).
- **Глобальное распределение**: аккаунт с provisioned throughput может реплицировать данные в любое число регионов. Режим single-region writes позволяет читать из многих регионов при записи в один; multi-region writes позволяет писать в любой добавленный регион.

### 4. Оценка пригодности сервиса для нагрузки
Источник: https://learn.microsoft.com/en-us/training/modules/explore-azure-cosmos-db-nosql/4-evaluate-azure-cosmos-db-for-workload

- **Признаки, что сервис подходит**: быстро меняющиеся данные (varied shapes, эволюция структуры); переменная нагрузка; требование предсказуемой низкой задержки; критичность для бизнеса (строгие требования RTO и RPO).
- **Сценарии**: каталоги и корзины покупок, back end для web и mobile, IoT-телеметрия, игры.
- **AI-сценарии**: одна база может быть операционным хранилищем, источником данных для grounding (RAG) и памятью агента; векторы хранятся рядом с исходными данными, без отдельной векторной базы.
- **Когда сервис может не добавить ценности**: текущая БД уже удовлетворяет требованиям; корректность зависит от реляционного поведения (внешние ключи, join по независимым записям), хотя сервис поддерживает ACID-транзакции; основная нагрузка аналитическая (полные сканы, сложные агрегации); шаблоны доступа не позволяют эффективно партиционировать данные.

### 5. Ресурсы и базовые операции
Источник: https://learn.microsoft.com/en-us/training/modules/explore-azure-cosmos-db-nosql/5-explore-resources-basic-operations

- Data Explorer в портале показывает иерархию аккаунт - база - контейнер - элемент и позволяет создавать ресурсы, просматривать и редактировать JSON, выполнять запросы без кода. В продакшене ресурсы обычно создают как инфраструктуру как код (Bicep, ARM, Azure CLI, Azure PowerShell).
- **Аккаунт**: выбирается API (NoSQL, фиксируется навсегда), имя, регион, режим емкости (provisioned throughput или serverless). Throughput с autoscale задается позже, при создании базы или контейнера.
- **База данных**: нужна только уникальность имени в аккаунте.
- **Контейнер**: родительская база, уникальное имя, путь partition key (например, `/categoryId`); путь нельзя изменить на месте - нужна копия данных в новый контейнер.
- **Элементы**: JSON-документ; если не указать `id`, Data Explorer сгенерирует его, сервис добавит системные свойства `_rid` и `_etag`. В коде `id` лучше задавать явно.
- **Запросы**: SQL-подобный язык. `SELECT * FROM product p` возвращает все элементы контейнера; `SELECT * FROM product p WHERE p.categoryId = "..."` - фильтр по partition key, который обращается к одной логической партиции. FROM задает имя для элементов внутри одного контейнера, а не таблицу; join между контейнерами невозможен.

### 8. Итоги
Источник: https://learn.microsoft.com/en-us/training/modules/explore-azure-cosmos-db-nosql/8-summary

Azure Cosmos DB for NoSQL - полностью управляемая NoSQL- и векторная база с документами JSON в иерархии аккаунт - база - контейнер - элемент. Масштабирование объясняют три идеи: RU как единица throughput, партиционирование и глобальное распределение. Решение о подходимости принимается по сигналам нагрузки и по случаям, когда лучше реляционная БД или другой API.

## Важные команды / код / настройки

- Пример элемента (клиент): JSON с полями `id`, `type`, `customerId`, `firstName`, `lastName`, `emailAddress`, `addresses`, `salesOrderCount`.
- Пример элемента каталога: `{ "categoryId": "...", "categoryName": "Components, Pedals", "sku": "PD-R563", "name": "ML Road Pedal", "price": 62.09 }`.
- Запрос всех элементов: `SELECT * FROM product p`.
- Запрос по категории (фильтр по partition key): `SELECT * FROM product p WHERE p.categoryId = "4F34E180-384D-42FC-AC10-FEC30227577F"`.
- Пути partition key задаются при создании контейнера, например `/categoryId`.
- Лимиты: физическая партиция до 10 000 RU/s и 50 GB; логическая партиция до 20 GB.
- Autoscale: throughput между 10% и 100% заданного максимума.
- Уровни согласованности: strong, bounded staleness, session, consistent prefix, eventual.
- Эталон стоимости: точечное чтение 1 KB элемента = 1 RU.

## Что запомнить

- Иерархия ресурсов: аккаунт (регионы и API) - база данных - контейнер (масштабирование) - элемент (JSON).
- Request units делают стоимость операций предсказуемой: точечное чтение 1 KB = 1 RU.
- Partition key определяет масштабирование и стоимость запросов: равенство по ключу направляет запрос в одну логическую партицию.
- Глобальное распределение добавляет регионы онлайн; режим multi-region writes позволяет писать в любой регион.
- Сервис подходит для быстро меняющихся схем, переменной нагрузки и AI-сценариев с векторами, но не для основной аналитики и строго реляционной модели.
