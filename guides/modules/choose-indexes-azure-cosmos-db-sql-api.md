# Выбор индексов в Azure Cosmos DB for NoSQL (SQL API)

**Источник:** https://learn.microsoft.com/en-us/training/modules/choose-indexes-azure-cosmos-db-sql-api/

## Цель модуля

Научиться настраивать индексную политику контейнера Azure Cosmos DB for NoSQL под рабочую нагрузку: read-heavy (много чтений по разным полям) и write-heavy (много записей больших документов), с учетом способов выполнения фильтров (index seek, index scan, full scan).

## Ключевые понятия

- **Schema-agnostic (без схемы)** - Azure Cosmos DB for NoSQL по умолчанию индексирует все пути и значения документа.
- **Indexing policy (индексная политика)** - набор правил, какие пути JSON включаются в индекс и исключаются из него (`includedPaths`, `excludedPaths`, `indexingMode`, `automatic`).
- **Inverted index (инвертированный индекс)** - структура, в которой для каждого пути и значения известны элементы, содержащие это значение.
- **Index seek** - точный поиск значения в индексе; стоимость поиска постоянна, а загрузка найденных элементов растет линейно с их количеством.
- **Index scan** - перебор возможных значений поля и сравнение с фильтром; стоимость немного выше seek и зависит от кардинальности свойства. Бывает точным (precise) и расширенным (expanded).
- **Full scan (полное сканирование)** - загрузка всех элементов контейнера для вычисления фильтра; индекс не используется, стоимость растет с общим числом элементов.
- **RU/s** - единицы запроса в секунду, которые расходуются на операции, включая индексирование записей.
- **Index rebuild (перестроение индекса)** - требуется при изменении индексной политики.

## Содержание по урокам

### 1. Введение
Источник: https://learn.microsoft.com/en-us/training/modules/choose-indexes-azure-cosmos-db-sql-api/1-introduction

Индексная политика по умолчанию индексирует все пути и значения. Ее можно настроить, чтобы уменьшить потребление RU/s для write-heavy нагрузок с большими документами. Цели модуля: настроить индексную политику для read-heavy и для write-heavy нагрузок.

### 2. Использование индекса
Источник: https://learn.microsoft.com/en-us/training/modules/choose-indexes-azure-cosmos-db-sql-api/2-index-usage

Движок выбирает один из трех способов вычисления фильтров: index seek (точное совпадение), index scan (перебор значений индекса, включая бинарный поиск для диапазонов и строковых функций) и full scan (загрузка всех элементов, индекс не используется). Разобран пример с тремя элементами (name, price): фильтр `p.name = 'Touring-1000 Blue'` выполняется как index seek, `p.name IN (...)` - как seek по нескольким значениям, а диапазон `p.price >= 500 AND p.price <= 1000` - как index scan. Вывод: запросы с диапазонами и строковыми функциями часто требуют index scan; оптимизируйте фильтры так, чтобы использовать самый эффективный метод.

### 3. Шаблоны индексации для read-heavy нагрузок
Источник: https://learn.microsoft.com/en-us/training/modules/choose-indexes-azure-cosmos-db-sql-api/3-review-read-heavy-index-patterns

По умолчанию контейнер индексирует корневой путь `/*`, исключая `/"_etag"/?`. Для read-heavy нагрузок лучше индексировать как можно больше полей. Если часть свойств (например, большое description и metadata) никогда не используется в фильтрах, их можно исключить. Предпочтительный подход - индексировать все по умолчанию и выборочно исключать пути, потому что приложение получает новые поля для запросов сразу. Изменение политики требует перестроения индекса.

### 4. Шаблоны индексации для write-heavy нагрузок
Источник: https://learn.microsoft.com/en-us/training/modules/choose-indexes-azure-cosmos-db-sql-api/4-review-write-heavy-index-patterns

Каждая вставка или обновление запускает индексатор, поэтому большие документы и массовые загрузки потребляют много RU/s. Если приложение фильтрует только по `price`, индексная политика может включать только `/price/?` и исключать `/*`. Если приложение пишет интенсивно и читает только точечно по `id` и partition key, индексирование можно полностью отключить (`"indexingMode": "none"`).

## Важные команды / код / настройки

- Политика по умолчанию: `"indexingMode": "consistent"`, `"automatic": true`, `"includedPaths": [{ "path": "/*" }]`, `"excludedPaths": [{ "path": "/\"_etag\"/?" }]`.
- Исключить большие и неиспользуемые пути при индексировании всего остального: `excludedPaths` с `"/description/?"` и `"/metadata/*"` при `includedPaths` = `"/*"`.
- Индексировать только нужные пути: `includedPaths` с `"/name/?"` и `"/price/?"`, `excludedPaths` с `"/*"`.
- Минимальная политика для фильтров только по цене: `includedPaths` = `"/price/?"`, `excludedPaths` = `"/*"`.
- Отключить индексирование: `"indexingMode": "none"` (для записи и точечных чтений по `id` и partition key).
- Пример фильтра, который использует index seek: `SELECT * FROM products p WHERE p.name = 'Touring-1000 Blue'`.
- Пример фильтра, который использует index scan: `SELECT * FROM products p WHERE p.price >= 500 AND p.price <= 1000`.

## Что запомнить

- По умолчанию индексируется весь документ, поэтому каждая запись тратит RU/s на индексирование всех путей.
- Index seek дешевле index scan, а full scan (без использования индекса) самый дорогой и растет с числом элементов контейнера.
- Для read-heavy нагрузок индексируйте как можно больше путей; для write-heavy исключайте неиспользуемые пути.
- Предпочтительный подход - индексировать все и выборочно исключать пути.
- Изменение индексной политики требует перестроения индекса, поэтому планируйте ее заранее.
